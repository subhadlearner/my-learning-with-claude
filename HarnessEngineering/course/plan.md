# Course plan (spoilers: contains the answers to the check questions)

This file is the day-by-day plan the daily routine follows. The weekly planning routine adds each new block at the end. Edit it to change what a day teaches.

## Block 1 spine: Why a harness exists (4 to 20 October)
Each day gives: the title question, IDEA (stated only at the end of the nugget), PATH (the first-principles route for the steps; you write the steps, following this route), BUILDER (today's addition to the analogy), TRY, SUBHFORGE (section numbers refer to design/V0.2-ARCHITECTURE.md unless "Contracts" is named, which means design/V0.2-WORKFLOW-CONTRACTS.md), CHECK, ANSWER (given at the start of the next day), LINK (the words to add to the chain).

Day 1, 4 Oct. "Where does the model keep your project?" IDEA: the model knows only the general skill frozen into it and the text in front of it; your project must always be put into that text by something outside the model. PATH: a model is physically a file of numbers, frozen after training → using it runs arithmetic and leaves the file byte-for-byte unchanged → so yesterday can live only in the file or in the text handed over, and the file is ruled out → chat seems to remember only because the app resends the whole transcript every turn. BUILDER: he knows only the papers put in his hands this morning. TRY: in a new chat ask "what did we decide yesterday about error handling?", then paste the decision and ask again. SUBHFORGE: the vision lists "lost context" and "repeated explanation" first among things to minimise (§1). CHECK: A coding agent "remembers" your coding conventions across sessions. What must be happening? ANSWER: something outside the model saved them as text and puts them back in front of it each session. LINK: remembers nothing.

Day 2, 5 Oct. "Why does the same question get different answers?" IDEA: the same input can give different outputs, and how confident the wording sounds tells you nothing about whether it is right. PATH: the arithmetic does not produce a word; it produces a likelihood for every possible next piece of text → one is picked by a weighted dice roll → it is appended and the process repeats, so one different early roll changes everything after it → nothing in this mechanism marks a roll as wrong; a wrong answer is made the same way and reads just as fluent. BUILDER: ask him the same question on two mornings and get two different answers, each given with the same assurance. TRY: ask the same design question in two fresh chats and compare. SUBHFORGE: "repeated semantically identical failures stop instead of burning budget" (§22). CHECK: An agent writes "all tests pass" in a confident sentence. What does the confidence tell you? ANSWER: nothing; fluent wording comes from the same dice process whether the statement is true or not. LINK: output varies.

Day 3, 6 Oct. "How does a text function get any work done?" IDEA: an agent is the model called in a loop by a program; the program does the acting and feeds each result back as text. PATH: the function only returns text, and text cannot run a test → so a program reads the text, and when it says "run this command" the program runs it → the result is added to the text and the model is called again → this repeats until the text says it is finished; the model never touches your files, the program does. BUILDER: he never leaves the site office; he writes instructions on slips, a runner carries them out and brings back a note of what happened. TRY: open one finished task in Kilo and look at its step list: each tool call is a slip, each result a note. SUBHFORGE: "Execution combines: SubhForge lifecycle rules; specialized agents; deterministic utilities" (§4.3). CHECK: When an agent "edits a file", who actually edits it? ANSWER: the program around the model, following text the model wrote. LINK: works through a loop.

Day 4, 7 Oct. "Why do long tasks go wrong even with a good model?" IDEA: small error rates multiply across steps, so a long task fails often unless something outside the loop catches errors along the way. PATH: each step has some chance of being off (Day 2) → each step builds on the last one's output (Day 3), so an error is carried forward, not averaged away → arithmetic: 95% right per step over 20 steps is 0.95^20, about 36% → a better model raises the per-step number but the multiplying remains. BUILDER: twenty slips in a row; one misread measurement on slip 3 and seventeen more are built faithfully on it. TRY: work out 0.9^10, 0.95^20 and 0.99^50 on a calculator. SUBHFORGE: "Failures should be: detected → contained → diagnosable → recoverable" (§3.8). CHECK: Why does a smarter model not remove the need for checks on long tasks? ANSWER: it raises each step's odds, but the odds still multiply; only a check outside the loop stops an error being carried forward. LINK: errors compound.

Day 5, 8 Oct. "If he forgets everything, where must the plan live?" IDEA: anything that must survive is deliberately written to a durable place outside the model and deliberately read back. PATH: list what must outlive a session: decisions, what is done, what is next → it can sit in the model (ruled out, Day 1), in the text of this session (gone when it ends), or outside in a file → so it is written outside, in a known place → writing is only half; it must be handed back at the start of the next session → a chat history is not this: it exists by accident and gets cut off. BUILDER: the site diary and the drawings, kept in the site office and handed to him at the gate. TRY: for your current project, ask: if every chat were deleted today, what would be lost? SUBHFORGE: "Interrupted work must resume from durable authority, not model memory" (§3.8). CHECK: What separates durable state from a chat history? ANSWER: it is written on purpose, in a known place, and read back on purpose. LINK: truth written outside.

Day 6, 9 Oct. "What happens when two documents disagree?" IDEA: each fact needs exactly one home; everything else points to it. PATH: truth now lives in files (Day 5) → suppose one fact sits in two files and only one gets updated → the model sees whichever file it is handed (Day 1) and cannot know the other exists → a person would notice and ask; the model carries on, sounding sure (Day 2). BUILDER: two sets of drawings, one revised; he builds from whichever he is handed. TRY: search your repo for one fact that is written in two places. SUBHFORGE: canonical documents evolve in place, no "prd-v2.md" (§4.1); his design folder follows "Every rule has exactly one authoritative home" (design/README.md). CHECK: Why is a duplicated fact more dangerous for an agent than for a team of people? ANSWER: people notice the conflict and ask; the model reads the copy in front of it and proceeds. LINK: one home per fact.

Day 7, 10 Oct. "Is 'what we are building' the same kind of fact as 'what is done'?" IDEA: slow-changing meaning, fast-changing work state and computed views are kept apart, and a view is never stored as truth. PATH: some facts change rarely and deserve review: what the product is → others change every hour: which job is in progress → kept together, the churn buries the meaning → a third kind is only an answer worked out from the other two, such as a status report; store and edit it and you have made a second copy (Day 6). BUILDER: the drawings, the job board, and the foreman's daily summary, which he reads off the board and never writes on. TRY: find one status document in a project of yours and ask whether it could be regenerated. SUBHFORGE: Product Truth in Git (§4.1), an Operational Work Graph (§4.2), and "Derived views such as status and work plans are projections, not third stores of truth" (§4.3). CHECK: Why must a status report never be edited by hand? ANSWER: it is computed from the real stores, so an edited copy becomes a second home for the same facts and drifts. LINK: kinds of truth kept apart.

Day 8, 11 Oct. "Why not hand him everything?" IDEA: what goes in front of the model is a budget, and choosing it is a design decision. PATH: the text the model can take in has a hard size limit → well before the limit, a key line among thousands gets less weight, so quality falls as it fills → every piece of text also costs money and time → and since truth lives outside (Day 5), someone must choose what to bring in. BUILDER: handing him the whole filing cabinet at the gate, against today's three sheets. TRY: look at how much text one of your typical agent tasks loads. SUBHFORGE: context targets of roughly 20–40k tokens working and a 100k ceiling: "stop rather than silently overflow" (§21.1); "Do not load broad project history by default" (§21.2). CHECK: Why is "give it the whole repo to be safe" the wrong instinct? ANSWER: more text thins attention and raises cost, so the lines that matter are more likely to be missed. LINK: context is a budget.

Day 9, 12 Oct. "How big should one job be?" IDEA: a good unit of work fits in one context and can be checked on its own; that is what a spec is. PATH: the job plus everything it needs must fit the budget (Day 8) → a shorter chain of steps is more reliable (Day 4) → and you must be able to tell this job is finished without finishing other jobs → so the right size is set by two tests: fits in one context, checkable alone. BUILDER: a work order for one room, with a way to inspect that room by itself. TRY: take one task you gave an agent recently and apply the two tests. SUBHFORGE: Spec artifact target of roughly 5–15k tokens (§21.1); "Specs represent implementation-ready behavioral slices" (§3.6). CHECK: Name the two properties of a good unit of work for an agent. ANSWER: it fits in one bounded context, and its completion can be verified independently. LINK: work cut to fit.

Day 10, 13 Oct. "When he says 'done', what do you have?" IDEA: the model's "done" is a claim; it becomes a fact only when something else checks the work and leaves a record. PATH: "done" is text made by the dice process (Day 2) → a true "done" and a false one look identical → so someone must look at the work itself, not at the sentence → it cannot be the same builder, who has the same blind spots → and the check must leave a record, or it is just another claim. BUILDER: the inspector, and the signed inspection sheet. TRY: find the last time an agent told you something was finished and ask what you actually checked. SUBHFORGE: "verification facts are separate from judgement" and "verification reports are immutable evidence" (Contracts §23.1). CHECK: Why can the agent that wrote the code not certify it? ANSWER: its certificate is another output of the same process with the same blind spots; it adds confidence, not evidence. LINK: claims need evidence.

Day 11, 14 Oct. "Who should the inspector be?" IDEA: whatever software can prove is checked by ordinary code; the model and the human are kept for judgement. PATH: questions come in two kinds: ones with a computable answer (do the tests pass, is this move allowed) and ones needing judgement (is this design sound) → code answers the first kind the same way every time → a model check is one more dice roll (Day 2) and one more step that can be wrong (Day 4) → so everything computable goes to code. BUILDER: the tape measure and the spirit level for what can be measured; the architect's eye for what cannot. TRY: list three checks in your workflow and mark each "computable" or "judgement". SUBHFORGE: "Use deterministic code for things software can prove reliably" (§3.3); invariants carry an enforcement mode of DETERMINISTIC, SEMANTIC or MIXED (§5.3). CHECK: What is the test for whether a check belongs in code? ANSWER: if the right answer can be computed without judgement, it belongs in code. LINK: code checks what code can prove.

Day 12, 15 Oct. "Is yesterday's inspection still good today?" IDEA: evidence is about one exact version; when the thing changes, the evidence no longer applies. PATH: the sheet says "this wall, as it stood on Tuesday, passed" → on Wednesday the wall is changed → the sheet is still true, but about a wall that no longer exists → so every piece of evidence must name the exact version it checked, and stops counting when that version changes. BUILDER: an inspection sheet with the date and the drawing revision written on it. TRY: think of a test run you trusted after the code had changed. SUBHFORGE: "evidence freshness must match the implementation identity it claims to prove" (Contracts §23.1). CHECK: Tests passed yesterday and the code changed today. What exactly do you know? ANSWER: only that yesterday's version passed; about today's you have a claim until it is checked again. LINK: evidence expires.

Day 13, 16 Oct. "Who decides?" IDEA: decisions about meaning, risk and acceptance stay with the human, and "this is possible" is never "this is permitted". PATH: the model knows only the intent that is written down (Day 1), and what you want is larger than what is written → what it says is a claim (Day 10), and it bears no consequence for being wrong → so choices about what is wanted, what risk is acceptable and whether work is accepted belong to the person → and a job being ready to start is a fact, while starting it is a decision. BUILDER: the site owner signs off; scaffolding standing ready is not an instruction to build. TRY: recall a time an agent did something because it could, not because you asked. SUBHFORGE: when it cannot classify an ambiguity "it does not guess" (§3.4); a dependency is "never permission to act" (§3.5). CHECK: What is the difference between work being ready and work being authorised? ANSWER: ready is a fact about dependencies; authorised is a decision by the person. LINK: the human decides.

Day 14, 17 Oct. "What breaks when the plan changes?" IDEA: when the truth changes, you must find exactly which finished work it undermines and stop where the change stops mattering. That is reconciliation. PATH: each fact has one home (Day 6), jobs were cut from it (Day 9), each holds evidence tied to a version (Day 12) → the owner changes a drawing → some finished rooms were built to the old drawing, so their sheets no longer count; other rooms are untouched → the job is to find precisely which, and standing downstream is not the same as depending on what changed → the owner approves before anything is redone (Day 13). BUILDER: the change order. TRY: pick one requirement in a project and trace what would need redoing if it changed. SUBHFORGE: "analyse → human approve → apply", and "propagation stops at the first unaffected branch" (Contracts §16). CHECK: Why not simply mark everything downstream as affected? ANSWER: it throws away evidence that is still valid and creates work that has no cause. LINK: change is reconciled.

Day 15, 18 Oct. "What if he is interrupted halfway?" IDEA: every change to the outside truth must be safe to run again. PATH: the loop can stop at any moment: a crash, a limit, a closed laptop → an operation with three writes stops after the second, leaving the truth half-changed → the next session remembers nothing (Day 1) and cannot tell → so each operation is built so that doing it twice leaves the same result as doing it once. BUILDER: "paint this wall white" can be repeated safely; "add one more coat" cannot. TRY: find one script of yours that would do damage if run twice. SUBHFORGE: idempotent reconciliation APPLY operations (Contracts §16.3); "never emit a success token first" (Contracts §2.4). CHECK: In one sentence, what does "safe to repeat" mean? ANSWER: running the operation twice leaves the world as it would be after running it once. LINK: safe to repeat.

Day 16, 19 Oct. "How do you find out what happened?" IDEA: the harness, not the model, records what was done as it happens. PATH: after a failure you ask what it did, in what order, and why it stopped → the model cannot tell you (Day 1), and its account would be a claim (Day 10) → so the program around it writes down each operation as it happens: what, on which item, the state before and after, which checks ran → entries share an identifier so a failure can be followed back to where it began. BUILDER: the site log, written and timed by the office, not recalled by the builder. TRY: after your next agent failure, see whether you can reconstruct the order of events without asking the agent. SUBHFORGE: "Kilo owns harness/runtime telemetry. SubhForge owns lifecycle observability." (§23A). CHECK: Why not ask the agent what went wrong? ANSWER: it has no memory of it, and whatever it says is a claim, not a record. LINK: a trace is kept.

Day 17, 20 Oct. "Can you rebuild the whole design from two facts?" IDEA: every part of a harness follows from "remembers nothing" or "output varies"; a rule that follows from neither is ceremony. PATH: remembers nothing → truth written outside → one home → kinds of truth; and limited input → budget → work cut to fit → output varies → claims need evidence → code checks → evidence expires → no stake → the human decides; change → reconciliation; interruption → safe to repeat and traced → two things come free: the model and the harness can be swapped, because nothing essential lives in them, and any rule can be tested by asking which fact forces it. BUILDER: walk the whole site once and name why each thing is there. TRY: pick one rule in your design and trace it back. SUBHFORGE: "Does this materially help Subhadeep design, build, verify, reconcile or resume his own projects?" (§3.1); "The machine owns coordination. Subhadeep owns judgement." (§38). CHECK: Pick any rule in your design: which of the two facts does it exist because of? ANSWER (give in the wrap-up): every necessary rule traces to one or both; one that traces to neither is a candidate for removal. LINK: one argument. For this day the steps may be single lines.

## Block 2: The loop in depth (26 Oct–1 Nov)
Same form as Block 1. SUBHFORGE references are to the feature/v0.2.0 branch, read on 25 October; the design folder has been reorganised since Block 1, so "Architecture" means design/architecture/SUBHFORGE-V0.2-ARCHITECTURE.md, "Workflow" means design/workflow/SUBHFORGE-V0.2-WORKFLOW-CONTRACTS.md and "PRD" means design/prd/SUBHFORGE-V0.2-PRD.md. The block opens up Block 1's link 3 (works through a loop): what the loop carries from turn to turn, how it stops, and what it leaves behind when it does.

Day 18, 26 Oct. "What exactly is handed to him each time he is asked 'what next?'" IDEA: the loop's whole state is the transcript, an ordered list of messages that is sent in full on every turn and grows by each slip and note; whatever is not in it does not exist for the next turn. PATH: Day 3 said the result is added to the text and the model is called again → look at that text: it is a list of labelled messages, each saying who wrote it (the standing instructions, your request, the model's slip, the runner's note) → one turn is one call: the whole list goes in, one new message comes out, and the runner's note is appended after it → the function remembers nothing (Day 1), so turn 9 knows what turn 3 found only because turn 3's note is still in the list → so the list is the loop's entire memory, and it grows every turn. BUILDER: the clipboard: every slip he wrote and every note the runner brought back, in order, handed to him whole each time he is asked what next. TRY: open one finished Kilo task and count its messages; check that each tool call added one slip and one note. SUBHFORGE: the transcript lives only inside a run: "No vector database or long chat transcript is needed for normal reconstruction" (Architecture §21). CHECK: The agent read a config file on turn 3. Why can it still use the value on turn 9, and what would make it lose it? ANSWER: the runner's note from turn 3 is still in the transcript sent on turn 9; take that note out of the list and, for the model, the value was never read. LINK: the transcript is the loop's state.

Day 19, 27 Oct. "How does the loop know when to stop?" IDEA: the ordinary stop is a reply that asks for no action; it means the model chose to stop, which is a claim about the task, not evidence that it is done. PATH: the program reads every reply: if it asks for an action it runs it, appends the note and calls again (Day 18) → if the reply asks for nothing, there is nothing to run and nothing to send back, so the loop ends → so the normal stop is decided by the model, inside its reply → that reply comes from the same dice process as any other text (Day 2) → so "the turn ended", "the task is finished" and "the work is right" are three different statements, and the stop gives you only the first, plus a claim of the second (Day 10). BUILDER: he stops writing slips and goes home; that tells you he stopped, not that the room is built. TRY: take the last message of a finished Kilo task and ask what in the record, other than that message, shows the work is done. SUBHFORGE: the Spec loop does not end where the builder stops: "READY Spec → Implement → focused tests → Verify → Review → Complete" (PRD FR-010). CHECK: The loop ended because the model sent a reply with no tool request. What do you know? ANSWER: only that the model chose to stop asking for actions; whether the task is finished, and right, is still a claim until something checks it. LINK: stopping is the model's claim.

Day 20, 28 Oct. "What if he never stops writing slips?" IDEA: every loop needs a limit held by the program, which the model cannot override, and the honest limit is on what the run spends (tokens, time, money) rather than on the number of turns. PATH: the normal stop happens only if the model chooses it (Day 19), and nothing guarantees that choice: a confused model can ask for one more action forever → every turn resends the whole growing transcript (Day 18), so each turn costs more than the one before → so the program must hold a limit that fires whatever the model writes → counting turns is only a stand-in: forty small turns can be cheap, five turns with huge notes can be ruinous; what actually runs out is tokens, time and money → so the limit is set on spend, and checked before each call. BUILDER: the office gives him an allowance of materials and hours for the job; when it is used up, work stops, whatever he says about being nearly finished. TRY: if a run starts at 10k tokens and each turn adds 2k, work out what turn 30 sends (68k) and what thirty turns send in total (about 1.2 million). SUBHFORGE: limits are checked before dispatch, and "An absent limit stops preflight; it is not read as unlimited" (Architecture §22). CHECK: Why can stopping not be left to the model, even a very good one? ANSWER: stopping is a choice made by the dice process that it may never make, and each extra turn costs more because the whole transcript is resent; only a limit held by the program is certain to fire. LINK: the loop is bounded from outside.

Day 21, 29 Oct. "How do you notice he is going round in circles before the allowance runs out?" IDEA: going round in circles is visible in the record as the same action with the same arguments repeated, so ordinary code can count exact repeats and stop the loop long before the budget would. PATH: the spend limit fires only at the end, after everything is spent (Day 20) → a common way to waste it: the same action with the same arguments and the same error, again and again; the dice can pick the same move each time and nothing in the model notices (Days 1–2) → every slip is in the transcript (Day 18), so the program can write down each action and its exact arguments and count repeats; that is computable, so it belongs in code (Day 11) → compare exactly, not by resemblance: "read lines 1–50" then "read lines 1–51" is progress, and asking a model whether two attempts are "the same" is one more dice roll → so after a small number of identical repeats the loop warns or stops. BUILDER: the runner is handed the same slip for the fifth time, with the same failed note in his pocket, and takes it to the office instead of the wall. TRY: in a failed agent run, look for one tool call repeated with identical arguments. SUBHFORGE: "Repeated semantically equivalent failures stop visibly" (PRD NFR-004). CHECK: Why compare actions exactly rather than ask a model whether two attempts are really the same? ANSWER: exact comparison is ordinary code that gives the same answer every time and never mistakes a small real step for repetition; a model judge is one more output that varies. LINK: circling is caught by counting.

Day 22, 30 Oct. "What should a failed check do to the loop?" IDEA: a check run by the program after each change can be fed straight back as the next note, turning the loop into fix-and-recheck; and that inner loop needs its own small repeat limit, after which it stops and hands over. PATH: an error caught late has already been built on (Day 4), and checks that can be computed belong to code (Day 11) → so after each edit the program itself runs the linter or the tests, without waiting to be asked → it appends the exact failure output to the transcript as a note (Day 18), so the next turn sees which line failed and why → the model tries again and the program checks again → but a model that cannot fix the error will keep producing new attempts, each different, so exact-repeat counting (Day 21) may never fire → so the fix-and-recheck loop gets its own small limit (Aider's default is three), and reaching it is a visible stop, not a retry until green. BUILDER: the inspector puts the spirit level on each wall as soon as it is built and pins the reading to the clipboard; after three failed attempts on the same wall, he calls the office. TRY: next time tests fail during an agent run, find whether the failure text reached the model's next turn, or only a summary of it. SUBHFORGE: "The Fix → Verify and Diagnose → Fix loops are bounded by the configured repeat limit", and "the loop is not retried until green" (Workflow §12). CHECK: Why does the fix-and-recheck loop need its own limit when the run already has a spend limit? ANSWER: an unfixable error makes it spend the whole budget on different-looking attempts that the repeat check cannot catch; a small cap of its own turns that into an early, visible stop for a person to look at. LINK: checks feed back, within a limit.

Day 23, 31 Oct. "What must be on the clipboard when work stops?" IDEA: whenever the loop stops, every action already started gets a closing note, even "interrupted, outcome unknown", and the stop itself records why it happened, because the next session knows only what the record says. PATH: the loop can be stopped from outside at any moment: you press stop, a limit fires, the laptop closes (Days 15, 20) → at that moment a slip may be out with the runner: the action has started but no note has come back → the transcript then holds a request with no result, and the next turn or session, which remembers nothing (Day 1), cannot tell whether it ran → so the program closes every open slip with a note, even "stopped before the result came back" → and it records why the run stopped, because "finished by its own claim", "allowance used up", "going in circles", "too many failed fixes" and "stopped by you" each need a different next step, and must not look alike in the record. BUILDER: when the whistle blows, the runner still comes back with a note for every slip in his hand, and the office writes on the clipboard why work stopped. TRY: stop an agent mid-command once and look at what its record shows for that command. SUBHFORGE: at a stop, "Persist established safe progress and report the precise reason and next invocation" (Workflow §17.4). CHECK: You stop an agent while a database migration command is running. What must the record show, and why? ANSWER: that the migration was started and its outcome is unknown, and that the run stopped because you stopped it; without that, the next session may assume it never ran, or that it finished. LINK: every stop is closed and labelled.
